# 主题组件设计准则

适用于 `themes/academic/academic_template.css` 里的组件层。这个文件既是主题基座也是组件库，改它之前先读这份准则——里面每条都是踩过之后才写下来的，反面例子都标了行号。

总纲一句话：**组件是「语义 + 皮肤」，不是「骨架」。**

作者在 Markdown 里写成什么结构，就渲染成什么结构。组件的职责是让一类东西**看起来是一类东西**（同一套圆角、边框、字号、配色），不是规定「图必须在左边」「必须是左右两栏」。

自检标准：**如果作者为了换个排法不得不改 CSS、或者换一个组件，那这个组件就写过头了。**

---

## 1. 布局归作者：组件不预设排法

`imginfo` 是这条准则的样板：**它只给一层皮肤，一行布局代码都没有。**

```css
imginfo {
  padding: var(--ii-pad-y) var(--ii-pad-x);   /* 四边内边距，不替任何一侧留位 */
  border / border-radius / background / box-shadow;   /* 皮肤 */
}
imginfo img { border-radius: 8px; box-shadow: 0 0 0 1px var(--ii-ring); }
```

（`academic_template.css:1387`）图放哪一侧、图和文字各占多宽、图多大，全由作者自己在里面套的 `<flex>` / `<grid>` 决定；不套容器直接把内容排队写进去，就顺着卡片竖着堆。

**规则**：任何为「某一种排法」写死的值 —— 内边距不对称、绝对定位、保底高度、固定尺寸 —— 都是组件在替作者做决定。

**反例**（改回这样就是开倒车）：
- `padding-left: calc(图宽 + 间距 + 内边距)` 写死 → 左边凭空多出一块空位，图不在左边就露出一条白
- 图片 `position: absolute` 钉在左侧、`width/height` 用变量定死 → 图不在左边时浮错位置；作者写 `h:` 想放大，行内 style 只盖住高、盖不住宽，图被拉变形
- `min-height` 保底 → 卡片被图框撑着，内容少时底下空一大块
- 再叠一层 `:has(> flex)` 去「检测作者写了没有」→ 判据是猜的，作者换个容器（`<grid>`、`<div>`）就失效

**一个组件只该有一种排法时**（比如 `timeline` 天然纵向）才写死方向，且必须配开关 —— 见下一条。

## 2. 只有「天生只有一种排法」的组件才写死方向，且必须配开关

- `timeline` 天然纵向、`funnel` 天然逐级收窄 —— 这类可以写死
- `flow` 默认横向，但要给 `[vertical]`（`academic_template.css:3344`）
- `iconitem` 只管自己这一条怎么排，「要横排几条、怎么对齐，用外面的 flex / grid 决定」（`:3784`）

写死方向时一定配一个属性开关。让作者去写自定义 CSS 是设计失误。

**对齐方式也算排法**，同样要给开关：`flow[center]` 让节点内容居中（`:3334`）。写这类规则时想清楚例外 —— `flow[center]` 里嵌套列表整块拉满宽、条目内部仍左对齐（`:3338`），否则多行文字参差不齐，比不居中更难看。

## 3. 变体只改 CSS 变量

`imginfo` 把可变值收进组件自己的变量（`:1387`）：

```css
imginfo {
  --ii-ink / --ii-ring / --ii-tint / --ii-pad-x / --ii-pad-y
}
```

新增一个变体 = 覆盖几个变量，一行一个（`feature` 就是这样，`:3516`）：

```css
feature[green] { --ft-ink: #006400; }
feature[red]   { --ft-ink: #c00000; }
```

- **不要**把整套规则复制一遍再改颜色 —— 改一处规则要记得改所有变体，必然漏。
- 尺寸、间距、颜色一律收敛到组件自己的变量，**不要往 `:root` 堆**。
- 颜色变体只改「强调色」（标题色 + 图片外圈描边 + 引用竖线），**容器底色/卡边框保持中性**，所以一排里混用几种颜色也不花（`:1520`）。
- 老组件（`card[red] { border-color: … }`，`:1168`）还没收敛，属于历史包袱；改到它们时顺手收敛。

## 4. 属性正交，自由叠加

每个属性只干一件事，实现上各写各的规则，组合由作者自由拼：

- `flow`：`[vertical]` `[compact]` `[solid]` `[center]` `now="N"`
- `imginfo`：`[green|red|yellow|gray]` `[compact]`

**不要造 `flow-solid-vertical` 这种组合名**，那会让变体数量指数爆炸，也让作者猜不到该怎么拼。

## 5. 一个容器，一种视觉手法

| 组件 | 视觉手法 | 行号 |
|---|---|---|
| `card` | 左锚 3px 粗边线 + 标题底纹栏 | `:1126` |
| `outline` | 虚线外框（同结构、更轻） | `:1631` |
| `blockquote` | **无左边线**，靠圆角 + 阴影 + 背景深浅分层 | `:226` |
| `imginfo` | 照片卡：大圆角 + 双层柔和投影，图带强调色描边 | `:1387` |
| `feature` | 细实线 + 右上角序号水印 | `:3457` |
| `metric` | 居中大字 + 顶部 4px 粗线 | `:1882` |
| `summary` | 通栏深蓝横幅 | `:1823` |
| `compare` | 浮动徽标标签 + 微阴影 | `:2045` |
| `figure` | 细描边 + 居中灰图注 | `:3704` |

**同一手法不要用两次**，这是最常见的退化。例子：`card` 内的 `blockquote` 原本带一条 3px 左强调线，但 `card` 自己已经是左锚线了 —— 一块内容里两条同样方向的粗线，层级反而读不出来，已改成浅底 + 小圆角（`:1158`）。

自检：把两种容器放同一页，**遮住文字只看轮廓**，能一眼认出是两种东西 → 合格。

## 6. 选择器与特异度

**别在组件内部用 `>` 硬绑层级。** 作者嵌套一层容器就会失配。真实事故：`imginfo > :is(h1…h6) ~ :is(h1…h6)`（副标题行规则）在作者把两个标题套进 `<flex column>` 后匹配不到，`#### 1856–1939 · 奥地利精神分析学派创始人` 从「小一号灰字」退化成 1.15rem 粗体蓝标题，撑成三行把卡片挤变形。改成后代选择器 `imginfo :is(h1…h6) ~ :is(h1…h6)` 才不管作者套几层都对（`:1470`）。

**组件内唯一该用 `>` 的地方是「间距」**：`imginfo > * + *`（`:1416`）只管组件自己的直接子元素，作者套了 `<flex>` 的那部分交给容器的 gap —— 加 `>` 正是为了**不**把手伸进作者的布局里。

**覆盖全局规则先算特异度。** `:root img { margin: auto }`（`:511`）特异度是 (0,1,1)，组件里要压掉它得写到 (0,1,3) 以上（带一个伪类 + 两个元素）。组件里那些看起来很长的选择器不是随手堆的，是算出来的。

**页面级 `.compact` 与组件 `[compact]` 并存**时，选择器要三态展开（`:1529`）：

```css
imginfo[compact],
:root.compact imginfo,
section.compact imginfo { … }
```

**组件内标题统一化。** `card` 里 `h1`–`h6` 一个样（`:1141`），作者写 `<h3>` 还是 `<h4>` 不该影响视觉层级。`imginfo` 里「紧挨着的第二个标题」自动降级成副标题行，也是同一个思路。

## 7. 间距：同组用容器 gap，换组用 margin-top

同一个组里的元素交给容器的 `gap`，组与组之间用各自的 `margin-top`。两者都用 `gap` 的话所有间距必然一样大，层级读不出来（`imginfo` 的纵向节奏，`:1416`：直接子元素一律 `margin-top: 10px`，只有「标题 + 副标题行」被副标题行规则的 `2px` 压过去）。

**注意这里的 `>`**：组件能管的只有自己的直接子元素。作者套了 `<flex>` / `<grid>` 的内容，间距归那层容器的 gap，组件的 `margin-top` 伸不进去、也不该伸进去——不然两层间距叠起来，卡片里到处是 26px 的空隙。

组件内自己写的元素（如 `imginfo blockquote p`）统一 `margin: 0`，避免和上面的节奏叠一层。

## 8. 深色底上的行内元素要一起过一遍

只要给组件加了**深色背景**的变体，就必须把 `mark` / `code` / `a` / `tag` 这几个行内元素一起处理，否则它们用默认色直接糊掉。

`flow[solid]`（深蓝 `#003f88`）是现成的例子（`:3270`）：`mark` 默认红 `#c00000`、`code` 默认 `#1f2328`，在这个底上对比度只有 1.6:1；`tag` 的底色又正好等于胶囊底色，不换就看不见。

**不要**用 `filter` 或透明度去糊，直接改颜色。

## 9. 改完必须验证

- **截图逐页看**。渲染命令见 `package.json` 的 `dev:*` 脚本，或：
  `npx marp <deck> --theme-set themes/academic/academic_template.css themes/academic/academic_CUST.css --html --allow-local-files --images png -o <dir>/s.png`
  （输出是 `s.001.png` 这样的前缀文件，用后即删）
- **`themes/academic/academic组件体系.md` 是回归样本**：每个组件一页演示。改哪个组件，就把它的「渲染效果」「变体」「写法」「排法」几页重新渲染看一遍，确认各变体和几种排法都没退化，也**没有一页溢出**。
- **CSS 语法错误会静默丢掉整份主题**：页面会退回 Marp 默认样式，控制台不一定有提示，报错只在 `renderer.log` 里的 `Failed to register custom theme`。改完先确认页面还是学术主题的样子（深蓝页眉 + 那套字体）。
- 临时 deck 要放在 `Examples/<目录>/xxx.md`（两层深度），主题里的素材路径是按这个深度写死的。

## 10. 注释与代码组织

组件区按固定顺序排：`/* ==== 名字 — 一句话 ==== */` → 注释块 → 规则。

注释块里写这三样：

1. **用法示例**（能直接复制进 md 的那种）
2. **变体列表**（一行一个，说明改了什么）
3. **为什么这么写 / 踩过的坑**（这一条最重要，别省）

仓库里的注释都是这个调子（`:226` 的引用块分层、`:3431` 的容器盒子选型，是最好的两个样本）。写「为什么」和「改之前会怎样」，不写「这里设了 padding」。下一个人（包括几个月后的你自己）改这个组件时，只有这些注释能拦住他踩同一个坑。
